## 一、什么是「静默失败」，以及为什么它是主要敌人

**这个项目的核心教训是：能报错的都是好的，不报错的才要命。**

**实测遇到的静默失败**（全部真实发生过）：

| # | 现象 | 为什么不报错 |
|---|---|---|
| **1** | 发得出去、收不回来 | socket 没开 `CAN_RAW_FD_FRAMES` —— **TX 正常零报错** |
| **2** | 观测语义全乱 | 顺序错了但**总维度相同**，校验只比元素数 |
| **3** | 一推横移就抽风 | 训练只见过前进 —— **数据通路可用，但策略没见过** |
| **4** | 电机不动 | **首次调用只切模式、不发目标** |
| **5** | 加了 kp 没变化 | **被 clamp 削平**（上限 500） |
| **6** | 一直读到同一个错误 | `error_id` **只增不减** |
| **7** | 摔倒保护不触发 | IMU 断线 → NaN → 判据恒 false |
| **8** | 限位"有"但等于没有 | 配置成 `±3.14` |
| **9** | 第二个电机收不到反馈 | 同总线同 ID **静默顶掉**回调 |
| **10** | 标零失败了但看起来成功 | 脚本**丢弃了返回值** |

> **⇒ 十个坑，零个会报错。**

**所以本仓库的设计原则是**：
> **能在软件层发现的问题，绝不留给真机去发现。**

这就是为什么有 `check_preflight.sh`（上电前）、`check_contract.py`（部署前）、
以及所有脚本都要**落盘**（事后可回溯）。

## 二、认知陷阱（技术之外的）

### 陷阱 1：以为「跑通了」就是「做对了」

**真实例子**：训练 ✅ / 导出 ✅ / CAN ✅ / 推理节点启动 ✅ ——
**但策略质量未达标，上真机未做。**

> **每一环都通 ≠ 整体能走。**

### 陷阱 2：在最后一环用力，而问题在第一环

**症状**：机器人走得难看 → 第一反应是改步态奖励。

**但真因可能是**：
- 上游参考运动数据太少
- 模型质量是猜值
- PD 语义没对齐

> **⇒ 症状出现的位置，往往离病因很远。**
> **这就是为什么流程图要分段画、每段要有判据。**

### 陷阱 3：一个人干所有角色时，最先牺牲的是「安全」

真实团队是分工的（本体/训练/部署/安全/数据）。
一个人全包时，**最容易被牺牲的是"安全"这个角色** —— 因为它**不产出任何可见成果**。

> **而它的代价是**：摔一次可能是几千块维修 + 几周等货。

### 陷阱 4：过时的文档会污染后续所有推理

**真实案例**：多份文档写「3D 打印件未到货」，导致得出「硬件全线卡住」的错误判断。
**实际早已到货并组装。**

> **教训**：文档要标日期；**关键事实要现查现证**。

## 三、关于「奖励/惩罚」的一个根本认知

**这条来自调研，但值得每个做 RL 的人知道。**

**用户的真实痛点**：「手工奖励改 5 次，全被 policy 规避。」

**调研发现的规律**（5 个方向独立收敛）：

> **问题不在"奖励没调好"，在「用奖励表达约束」这个做法本身。**

**三个原因**：

| # | 原因 |
|---|---|
| **1** | **奖励可交易，约束不可** —— 「走快点挣 100 分，撞一下扣 50 分」→ 最优策略就是**撞着走**。惩罚再大只是抬价 |
| **2** | **折扣因子让远期惩罚打折** —— 策略会**学会"在折扣最低的时候摔"** |
| **3** | **指示函数没有梯度** —— 「离撞 1cm」和「离撞 1m」收到的信号**完全一样（都是 0）** |

**⇒ 解法不是"把惩罚调大"，是「换任务表述」**：
- 从「**告诉策略别做什么**」→ 换成「**给它一段参考动作**」
- 参考动作**同时**约束了所有维度，**没有换路的空间**

> **这被实测验证**：手工奖励 5 次失败（步频 5.5Hz、滑移 0.40），
> 换成运动跟踪**一次成功**（步频 0.62Hz、滑移 0.11）。

## 四、关于「安全」的一个反讽

**调研发现**：那位研究方向最相关的学者（安全 RL 出身），
在转向人形后**把安全从"方法贡献"降级成了"局限章节里固定的忏悔项"** ——
出现在每一篇论文里，但**从未闭环**。

> **这是一个提醒**：
> **写进论文 Limitations 不等于解决。写进文档的"已知限制"也一样。**
>
> **本仓库专门有一页 [已知限制](已知限制.md)，就是要避免这个反讽。**

## 五、方法论教训

### 1. 判断仓库活跃度：看 `pushed_at` 不是 `updated_at`

**实测幅度**：某仓库 `updated_at` 与 `pushed_at` **差 25.8 个月**。
（`updated_at` 会被 star/issue 变动刷新，≠ 代码活跃度）

### 2. `-` 非交互环境下要显式拒绝，不能默认通过

**本仓库的 `confirm()`**：检测到不是 TTY 就**直接退出**，要跳过必须显式加 `--yes`。

> **否则脚本在 CI/管道里会静默通过人工确认步骤** —— 这又是一次静默失败。

### 3. 度量前先确认「你测的是不是你想测的」

**真实案例**：
- 测量脚本用了**错误的配置族**（PPO 的配置测 FlashSAC 策略）
- **单 env 评测比 32 env 低估 episode 长度 3.8 倍**
- `env_cfg_override` 是**替换非合并** → seed/DR 悄悄漏掉

> **⇒ 跨配置比数字之前，先确认聚合层级和配置族一致。**

### 4. 「挂大权重 ≠ 它会起作用」

**实测**：奖励表里 `joint_limit` 权重 **-10.0**，
但**触发率只有 0.2%**、峰值量级 2e-6 —— **完全空转**。

> **⇒ 奖励项要"审计"，不能只看配置。**
