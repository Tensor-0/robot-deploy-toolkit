## 一、⭐ 我们的接线（**实际要接的**）

### 1.1 拓扑

```
                    RDK X5（主控）
                   ╱            ╲
              串口 ╱              ╲ USB
                 ╱                ╲
        DM-IMU-L1              DM-USB2FDCAN
      (921600, ttyACM0)      (双通道 USB-CAN)
                                    │
                        ┌───────────┴───────────┐
                     can0 │                       │ can1
                        ▼                       ▼
              左腿：DM4340P_24V ×5      右腿：DM4340P_24V ×5
             （ID 从【下】往上 1→5）    （ID 从【下】往上 1→5）
                  脚踝=1 … 髋=5             脚踝=1 … 髋=5
                        │                       │
                        ▼                       ▼
                  120Ω 终端电阻            120Ω 终端电阻
```

⚠️ **注意编号方向**：ID 是**从脚踝往上**递增的（脚踝=1、髋=5），
和策略的关节顺序（l1=髋 … l5=脚踝）**正好相反** —— 见 §1.2 的红框。

**供电路径**：`24V 电池 → 分电板 → 各腿`（+ DM-USB2FDCAN 供电）

📷 图：`can_topology.svg`（矢量）· `can_topology.png`（位图）
源文件：`can_topology.dot`（改图就改它）

### 1.2 电机 ID 映射

| 部位 | 总线 | 电机 | 发送 ID (CAN_ID) | 接收 ID (MST_ID) |
|---|---|---|---|---|
| **左腿** | **can0** | DM4340P_24V ×5 | `0x01` ~ `0x05` | `0x11` ~ `0x15` |
| **右腿** | **can1** | DM4340P_24V ×5 | `0x01` ~ `0x05` | `0x11` ~ `0x15` |

> ⚠️ **两条腿各自从 ID 1 开始编号**（不是全局唯一）。
> **靠「总线 + ID」共同区分。**

> ⚠️ **can0 = 左腿、can1 = 右腿**（2026-09-17 实测裁决；此前 09-08 的"can2=左腿"结论是错的）。
> ⚠️ **测的那天接口还叫 can1/can2** —— 板载 CAN 先抢占了 `can0`，USB 适配器只能拿到 can1/can2。
> 禁掉板载 CAN（`systemctl disable can4.service` + 注释 `98-onboard-can.rules`）之后才变成 can0/can1。
> **接线一根没动，只是名字整体降了一位；任何脚本都别写死总线名。**
>
> 🔴🔴 **同批实测还推翻了「电机 ID ↔ 关节」的对应**（本文旧表未列此层，但配置依赖它）：
>
> | 物理位置（从下往上）| **本机 CAN ID** |
> |---|---|
> | 脚踝（最下）| **1** |
> | 膝 | **2** |
> | 髋 roll（侧摆）| **3** |
> | 髋 yaw（拧转）| **4** |
> | 髋 pitch（最上）| **5** |
>
> ⇒ 配置须写 **`motor_id: [5,4,3,2,1]`**（该列表按 l1..l5 = 髋→脚 索引）。
> ⚠️ **写反会让策略把"髋角"当"脚踝角"，观测与动作双向错位，且不报错。**
> ⇒ 逐关节实测 5/5 验证，方法见 `robot-deploy-toolkit/scripts/sample_motors.py`。

### 1.3 软件侧对应配置

`robots/dm10/robot.yaml` 必须与上表一致：

```yaml
motors:
    # ⚠️ 该列表按【策略关节顺序 l1..l5 = 髋→脚】索引，
    #    而 CAN ID 是从脚踝往上编的 ⇒ 必须倒序写！
    motor_id:        [5, 4, 3, 2, 1, 5, 4, 3, 2, 1]   # 髋=5 … 脚踝=1
    motor_interface: ["can0", "can1"]                  # can0=左腿, can1=右腿
    motor_num:       [5, 5]
    motor_model:     [2 × 10]                          # 2 = DM4340P_24V
    master_id_offset: 0
```

> ⚠️ **这里写 `[1,2,3,4,5,...]` 是错的**（本文 2026-09-17 之前一直这么写）。
> 写反的后果：策略以为在动髋、实际在动脚踝 —— **观测与动作双向错位，且不报错**。

### 1.4 ⭐ 终端电阻（**CAN 故障头号原因**）

```
左腿 can0 链末端 ── 1 个 120Ω
右腿 can1 链末端 ── 1 个 120Ω
                   ────────────
                   共 2 个
```

**出故障时的判据**：

| 现象 | 原因 |
|---|---|
| 通信**时好时坏** | 电阻缺失 → 信号反射 |
| **完全不通** | 电阻**过多**（>2 个）→ 总线负载过大 |
| **高速丢帧** | 电阻**不在物理两端** |

> **⇒ CAN 通信出问题，先数终端电阻，再查别的。**

### 1.5 其他要点

| 项 | 要求 | 来源 |
|---|---|---|
| 波特率 | **1 Mbps**（仲裁域）| 必须与电机一致 |
| `txqueuelen` | **1000**（默认 10 太浅）| 高频发帧会丢 |
| 反馈帧仲裁 ID | **恒为 `0x000`** | 电机身份在 **D0 低 4 位** |
| IMU | 串口 `/dev/ttyACM0` @ **921600** | 不经 CAN |
| **24V 电池** | **≥ 50V 必须充电** | 【官方】欠压会中途掉电跌倒 |

## 二、对上游的 4 个适配点

> 上游基线：`Roboparty/roboparty_deploy @ a8a0f15` +
> `roboparty_motors @ 118e569` + `roboparty_imu @ 7a6e6d2`
>
> 适配仓库：`rdk-roboparty-integration`（有 patch 文件）

| # | 问题 | 我们的修复 |
|---|---|---|
| **1** | DM 反馈帧 ID 均为 **Master_ID（实测 0x000）**，电机 ID 在 D0 低 4 位；原驱动按 `can_id == motor_id + offset` 过滤 → **永远收不到反馈** | CAN 回调改用 `set_can_key_extractor`（按 **D0 低4位** 分发），`can_rx_cbk` 加 D0 校验兜底 |
| **2** | DM-USB2FDCAN 固件把**所有帧标成 FD 帧**，内核只把 `canfd_frame` 投递给启用 `CAN_RAW_FD_FRAMES` 的 socket → **RX 全静默、TX 正常、零报错** | `MotorsSocketCAN::open()` 启用 `CAN_RAW_FD_FRAMES` |
| **3** | 限幅表只有 48V 模型（SpdMax 20 / TauMax 28）| **新增 `DM4340P_24V`**（yaml 里 `motor_model: 2`）|
| **4** | `roboparty_imu` **无 DM-IMU-L1 驱动**（55AA 协议）| 新增 `dm_imu_l1` 驱动：状态机 + CRC16 + 欧拉 ZYX→四元数 |

> ⚠️ **第 2 条是最恶心的**：TX 完全正常、零报错、RX 全静默。
> **如果你自己从零写驱动，这一条会让你怀疑人生。**
